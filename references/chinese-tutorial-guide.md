# 中文教程写作规范

> 综合参考：阮一峰、廖雪峰、JavaGuide、CS-Notes、Rust 中文社区教程、ai-agents-from-zero、极客时间等中文教程的常见写法。

本文件只规定中文课件的表达、章节组织和中文读者体验。图表、图片、代码、可保存练习块等跨语言课件格式看 `courseware-format.md`。

## 核心取向

中文教程要像一个认真带人的师傅：先把问题讲明白，再带学习者动手或推理，最后确认他是不是真的会了。不要写成资料汇编，也不要写成静态题库。

推荐主线：

```text
问题入口 -> 人话直觉 -> 术语和边界 -> 例子/代码/案例 -> 判断标准 -> 互动练习 -> 收束
```

好的中文课件应当让学习者在每章结束时知道三件事：

- 这章到底解决了什么问题。
- 我现在能判断、能解释、能动手做什么。
- 哪些地方我还容易混，下一次学习从哪里接上。

## 三层递进结构

**技术主题：**

```text
第一层：基础入门（30%）-> 建立概念，跑通第一个程序
第二层：核心能力（40%）-> 深度讲解，动手实践
第三层：进阶实战（30%）-> 原理深挖，项目/面试/考试应用
```

**非技术主题：**

```text
第一层：基础入门（30%）-> 建立概念框架，理解核心问题
第二层：深层理解（40%）-> 关键理论、案例、推导
第三层：批判拓展（30%）-> 不同学派、前沿讨论、自选专题
```

## 自然章节结构

不要把课件写成固定模板。每章必须形成学习闭环，但标题和组织方式要跟主题走。

一章对应一个可折叠模块，模块根目录的 `content.md` 只写章节前言：

- 这章要解决的核心问题。
- 学习者需要具备的前置条件；缺了就指出本章会补哪一小段。
- 本章小节目录，每个小节解决什么问题；具体文件和导航规则看
  `courseware-format.md`。
- 本章完成后能做出的判断、解释或操作。

真正的正文写进小节文件。小节拆分、合并和导航链接规则以
`courseware-format.md` 为准；这里强调中文写法：系统精讲和考试备考可以拆
得更细，但每个小节都要写成能独立学习的讲义，不要只有几段目录说明。

小节正文自然包含这些内容，不要求固定标题：

- 用真实问题、错误现象、工作场景或反直觉点开场，不要第一段就堆定义。
- 先用人话建立直觉，再给准确术语；初学者第一次见到的词，当场解释。
- 用小数字、小数据、短代码或具体案例起步，再过渡到真实规模。
- 在概念旁边给判断标准：什么时候用，什么时候不用，和相似概念怎么区分。
- 如果有真实常见误解，就放在相关知识点旁边顺手拆掉；没有就不要硬写。
- 需要学习者作答时，用 `study-*` 题块；链接、题块和导出规则看
  `courseware-format.md`。
- 小节末尾可以自然收束 2-5 条要点；不要写空泛的“建议下一步”。

课件生成不是把资料“压缩成笔记”。先考虑怎么把已有资料、PPT、教材或调研来源衔接起来：补前置、加过渡、换成人话、用小例子垫一下，再进入原材料里的术语、图、公式、代码或结论。非必要禁止浓缩删减；需要删减时，必须是因为用户目标、考纲范围、时间限制、摸底结果或明确指令支持这个取舍。

考试备考课里，“重点清单”只能当导航，不能当正文。凡是期末复习 PPT、考纲或老师材料点名“重点掌握”的内容，正文必须展开成可作答的讲义：概念解释、题型、步骤、例子、易错点和评分关键词。非重点可以压成一句识别说明，但不能把重点也压成目录式概述。

## 初学者入口要求

系统精讲不是把所有概念压进一章。面向初学者或弱前置学习者时，每个基础模块必须先搭入口，再进入术语和公式。

基础模块必须满足：

- 开头先给一个具体问题或场景，不要第一段就堆定义。
- 每个核心术语第一次出现时，用一句人话解释它“在解决什么问题”。
- 第一个例子使用小数字、小数据或日常/工程场景；不要直接使用真实模型规模、论文公式或复杂代码。
- 从例子到抽象概念之间要有过渡句，说明“这个小例子和真实系统哪里一样，哪里不一样”。
- 如果学习者画像里写着数学、语言、工具前置薄弱，要在相关小节补一个“够用前置”，只讲当前小节马上会用到的部分。
- 不要把“验证状态”“官方链接”“练习题”提前到概念还没讲清楚之前。
- 不要在课件正文里写“本机未安装”“未执行验证”“验证状态”这类生成过程说明。

弱写法：

> 向量是有序数列，矩阵是二维数组，张量是多维数组。Transformer 输入张量形状为 `[batch, seq, hidden]`。

好写法：

> 先想一个问题：模型看到一句话时，电脑里到底放的是什么？它不是中文句子，也不是 Java 对象，最后只能是一堆数字。我们先从一句 4 个词的小句子开始看，每个词用 8 个数字表示，这样才能一步步理解 `[batch, seq, hidden]`。

## 章末互动题写法

章末不要再写静态的“思考题 + 参考答案”。只要题目需要学习者作答，就用本地阅读器支持的 `study-*` 题块。

使用规则：

- 选择题用 `study-choice`，适合概念辨析、方案选择、面试追问和考试选择题。
- 判断题用 `study-truefalse`，适合拆常见误解和边界条件。
- 短答、解释题、场景分析、面试回答和考试主观题统一用 `study-input`。
- `answer` 写参考答案；`explanation` 写参考思路、解析、回答要点、常见追问或评分标准。
- 模块末尾如果需要综合检查，连续放几道普通题型，不要写成单独的 `checkpoint` 题。
- 面试导向模式下，题目可以是选择题、判断题或开放题；开放题的 `explanation` 要包含回答要点、常见追问和判断标准。

示例：

````markdown
### 互动题：Redis 为什么快？

先按自己的话写 3 点，不要直接看答案。

```study-input
id: 03-redis-fast-interview
question: 面试官问“Redis 为什么快”，你会怎么答？请写出 3 个原因，并说明它们分别解决了什么问题。
mode: multi
min_words: 80
hints:
  - 不要只说“因为在内存里”
  - 想想数据结构、网络模型和线程模型
  - 顺手想一想 Redis 什么时候也会变慢
answer: >-
  内存访问是基础，高效数据结构、I/O 多路复用和单线程避免大量锁竞争也很关键。
explanation: >-
  参考思路：先说内存访问是基础，再补充高效数据结构、I/O 多路复用和单线程避免大量锁竞争。
  回答时要说清“快在哪里”，也要知道持久化、慢查询、大 key、网络瓶颈会让它变慢。
  常见追问：为什么单线程还能快？Redis 6 之后多线程主要解决什么？
  判断标准：能否把原因和具体瓶颈对应起来，而不是背几个关键词。
mastery_tags: [interview, explain]
```
````

不要在同一章塞太多题。题目少一点，但要真的能暴露理解问题。

## 中文表达原则

### 1. 先讲人话，再给术语

先用日常语言建立直觉，再给出精确术语。

好写法：

> 可以把 Hook 理解成一个钩子：它把 React 的状态能力钩到函数组件上，让函数组件也能记住数据。这个钩子的学名叫 `useState`。

弱写法：

> `useState` 是 React 的一个 Hook API，用于在函数组件中管理状态。

### 2. 核心概念要有抓手

能类比就类比，优先用学习者熟悉的生活经验或已学知识。类比必须说明边界：哪里像，哪里不像。

没有好类比时，不要硬编。改成从一个更简单的问题一步步推出来。

### 3. 判断标准要明确

不要只说“是什么”，还要说明：

- 什么时候用？
- 什么时候不用？
- 和相似概念怎么选？
- 看到什么现象，说明理解可能错了？

能用对比表格就用表格；表格讲不清时，用两个具体场景对比。

### 4. 示例和练习要贴近中文读者

**技术主题：**

- 代码注释使用自然中文，不写英文注释的直译版。
- 只有学习者需要亲自运行代码时，才展示必要安装命令、运行命令和预期输出。
- 需要依赖版本时，只写会影响学习或运行结果的版本要求。
- agent 没有实际运行代码时，在聊天交付说明里讲清楚，不写进学生课件正文。

**非技术主题：**

- 每个关键概念配一个具体案例。
- 推导过程不要跳步。
- 练习可以是辨析题、论述题、场景分析或材料题。
- 标注必要来源，不大段复制原文。

### 5. 官方资料要嵌在知识点旁边

不要把官方文档和资源全部塞到课程末尾。讲到具体 API（应用程序接口）、
概念、定理、工具命令时，如果有高质量官方或权威资料，就在旁边补一条
短链接。链接位置、课程级来源和资源导出规则以 `courseware-format.md`
为准。

好写法：

> 深入看：React 官方文档的 [`useState`](https://react.dev/reference/react/useState) 页面适合查参数、返回值和常见用法；先学完本节再看，不要一开始就陷进 API 细节。

写法要求：

- 链接必须服务当前知识点，不要堆资源列表。
- 一句话说明“为什么现在看这个链接有用”。
- 技术主题优先官方文档、标准、源码；非技术主题优先教材、论文、课程大纲或权威资料。

### 6. 用学习者已有经验做迁移

如果学习者画像里记录了已会语言、工具或领域经验，要主动利用，但不要硬套。

示例：

- 学过 Java 再学 Python 装饰器：可以先类比成“给函数包一层可复用处理”，再强调它不是 Java 注解，运行时机制不同。
- 有后端经验再学 React 状态：可以把状态理解成“组件自己的内存”，但要说明它不是服务器缓存，更新会触发渲染。
- 有数学基础再学机器学习：可以用函数、向量和优化来解释，但不要默认他懂工程实现。

规则：

- 类比只在能缩短理解路径时使用。
- 类比必须说明边界：哪里像，哪里不像。
- 薄弱前置只补当前章节需要的一小段，不要偏题变成另一门课。

### 7. 误解和坑点就地拆

真实常见误解要写，但不要凑数量，也不要固定做成“踩坑表”。它应该自然出现在相关知识点旁边。

可用写法：

- “这里容易误会的是……”
- “如果你看到……，先查……，别急着……”
- “这个问题只在……场景下会出现；平时不用提前焦虑。”
- “它和 XXX 不一样，关键区别是……”

没有真实来源、真实经验或清晰场景时，不要写“常见陷阱”。

### 8. 版本说明只在影响学习时写

技术主题只有在 API（应用程序接口）、语法、工具链或依赖有破坏性变化时才写版本说明。

非技术主题标注教材版次、论文年份或数据时间即可，不硬凑“版本变化”。

### 9. 面试题不要变成背答案

面试导向模式下，每章可以关联 1-3 道典型题，但必须让学习者先作答。题目按题型写成 `study-choice`、`study-truefalse` 或 `study-input`，参考内容放在 `answer` 和 `explanation` 中。

`answer` 至少包含：

- 回答要点：应该覆盖哪些点。
- 追问方向：面试官可能继续问什么。
- 判断标准：什么回答算理解了，什么回答只是背词。

不要把面试题写成静态 Markdown 列表，也不要只给“标准答案”。

### 10. 术语、题库和闪卡不要旁路化

不要把术语、题库和闪卡写成没人消费的旁路材料。默认文件策略以
`courseware-format.md` 为准；本指南只规定中文正文该怎么呈现这些内容。

更好的写法：

- 术语第一次出现时顺手解释；术语多时，在本章末尾写“术语速查”。
- 面试题、考试题和课后练习写进本章，用 `study-choice`、`study-truefalse` 或 `study-input` 让学习者先答再看解析。
- 复习问题来自已学过的关键概念，由学习阶段写入 `concepts.json`，不要在课程生成阶段预制一堆没学过的闪卡。

### 11. 章节和小节收束要有信息量

小结不是把标题抄一遍。它应该帮学习者完成整理：

- 本章主问题是什么。
- 本章最重要的 3-6 个概念或判断标准是什么。
- 哪个例子最能代表本章方法。
- 下一章会接着解决什么缺口。

如果没有具体下一步，就不要写“建议下一步”。空泛的“完成练习后进入下一章”没有价值。

## 中文禁忌

- 不要英文直接机翻；用中文思维重写。
- 不要堆术语不解释。
- 学习者需要亲自运行的代码，不要只给代码而不给必要运行命令和预期输出。
- 不要把 agent 的本机环境、验证状态、缺少依赖等过程信息写进课件正文。
- 不要只讲是什么，不讲为什么和怎么选。
- 不要忽略影响学习结果的版本变化。
- 不要大段照搬官方文档；在具体知识点旁边放短链接即可。
- 不要写 AI 腔：夸大意义、三段式排比、空洞连接词、宣传话术。
- 不要为凑结构硬写“常见陷阱”“建议下一步”“面试题”。
- 不要写固定口号式标题，例如每节都来一句“先记住一句话”。
