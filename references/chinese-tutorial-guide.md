# 中文教程写作规范

> 综合参考：极客时间《MySQL实战45讲》（丁奇/林晓斌）、《小林 coding 图解系统/网络》、阮一峰、廖雪峰、Rust 中文社区教程等国内顶尖技术专栏的写法。

本文件只规定中文课件的表达、章节组织和中文读者体验。图表、图片、代码、可保存练习块等跨语言课件格式看 `courseware-format.md`。

## 核心取向

中文教程要像一个带人的师傅：先把问题讲明白，再带学习者动手或推理，最后确认他是不是真的会了。不要写成资料汇编，也不要写成静态题库。

## 教学口吻与叙事心法：像《MySQL实战45讲》一样由浅入深、抓人眼球

优秀中文技术专栏（如丁奇《MySQL实战45讲》）之所以让人一口气读完还记得住，靠的不是干巴巴的教材定义，也不是幼稚的童话比喻，而是以下四个核心手法：

1. **一条最小真实案例贯穿全节（One Concrete Case End-to-End）**：
   - 开头先给一个最简单、最具体的真实操作（比如《MySQL实战45讲》第 1 讲开头只写一条 `select * from T where ID=10;`，然后全文带着读者跟着这条语句走遍连接器、查询缓存、分析器、优化器、执行器）。
   - 整节的所有小标题、图解和推演都围绕**这同一个具体例子**展开。**严禁东一榔头西一棒槌**（不要第一段讲屏幕打字、第三段突然扯虚拟机、第四段又跳去讲网卡发包）。
2. **新名词当场拆透，严禁“用未学黑话解释当前概念”（Zero Forward-Jargon）**：
   - **绝不超前抛词**：在第 1 章讲基础概念时，严禁随口甩出后文才学的底层词（如还没讲网络和文件系统就抛“以太网帧、socket、文件描述符、陷入指令、页表快表”）。如果全局架构图里不得不出现某个后续模块名，必须当场用一句话大白话说清它的作用，并明确给读者托底：“至于它内部怎么实现，我们会在后面第 X 章专门展开，这里你先知道它负责……即可。”
   - **新词出场三步拆解法**：每当引入本节必须掌握的新术语（如“端口地址”“状态寄存器”“词法分析”“可重复读”），绝不能只写个名字就滑过去，必须结合当前例子用 2～3 句大白话交代清楚：① **它接什么输入**；② **它具体做了什么动作**；③ **做完后输出什么（或写错了会报什么具体错误）**。
3. **顺着读者直觉“自我追问”推进（Anticipatory Q&A Flow）**：
   - 每讲完一个正向机制，立刻替读者问出那个最自然的追问，用真问题引出深层机制或工程取舍。例如：
     - *“看到这儿你可能会问：**既然建立连接这么慢，那我全都用长连接一直不断开不就好了吗？**但实际跑起来你会发现……”*
     - *“**大多数情况下我反而建议你不要使用查询缓存，为什么呢？**因为只要对表有一次更新……”*
     - *“**你肯定会想：既然已经有 PC 寄存器记住地址了，为什么还要多此一举加一个 MAR？**我们试着只用 PC 走一步看看会出什么乱子……”*
4. **充分发挥 Markdown 立体排版优势（按语义角色使用格式，拒绝平文本砖墙）**：
   - **`##` 二级标题标记主线案例的每一站**：每当主线例子走入下一个组件、阶段或关键追问（就像《MySQL实战45讲》顺着一条 SQL 依次立下 `## 连接器`、`## 查询缓存`、`## 分析器`），自然设立一个具体的 `##` 标题，同时为页面生成清晰的目录（TOC），切忌整篇只有一个 `#` 大标题从头闷头写到底。
   - **`**加粗**` 承担“结构路标”与“反直觉点睛”**：不靠死板次数限制，而是按角色精准使用加粗——① **首次正式定名的核心概念**；② **列表项的领头锚点**（如 `- **长连接**：连接成功后持续复用...`）；③ **段落中最核心的那句反直觉判断或避坑结论**（如 `**但是大多数情况下我会建议你不要使用查询缓存，为什么呢？因为查询缓存往往弊大于利。**`）。既不要在普通句子里给一般动词、形容词频繁加粗当说话重音，也**绝不能因噎废食写成全文零加粗的平文本**。
   - **列表、代码块/报错现场、提示框（`> [!TIP]`）与分步讲台立体配合**：遇到分支情况（如“认证失败 vs 认证通过”）、并列方案或有序执行步骤，自然拆成无序/有序列表或对比表；关键工程经验与考场避坑点用 `> [!TIP]` / `> [!WARNING]` 提示框拎出，避免把所有信息揉成一整面灰白文字墙。

### 标杆片段示范（《MySQL实战45讲》风格 vs 平文本反例）

好写法（一条真实案例贯穿 + 新词拆透输入/动作/报错 + 追问转折 + 层次分明的 Markdown）：

```markdown
## 分析器：MySQL 怎么知道你要干什么？

如果没有命中查询缓存，就要开始真正执行语句了。首先，MySQL 需要知道你要做什么，因此需要对开头那条 `select * from T where ID=10;` 做解析。

- **词法分析**：你输入的是由多个字符串和空格组成的一条 SQL 语句，MySQL 需要把它们拆开并认出每个词代表什么。它从 `select` 关键字认出这是一条查询语句，把字符串 `T` 识别成**表名 T**，把字符串 `ID` 识别成**列 ID**。
- **语法分析**：接着根据语法规则，判断你输入的这条 SQL 是否满足 MySQL 语法。

如果你的语句写错了，就会在这一步收到 `You have an error in your SQL syntax` 的错误提醒。比如把开头的 `select` 少打了一个字母 `s`：

```sql
mysql> elect * from T where ID=10;
ERROR 1064 (42000): You have an error in your SQL syntax; ... near 'elect * from T where ID=10' at line 1
```

> [!TIP]
> **排查语法报错时，直接盯紧报错信息里 `use near` 后面紧跟的内容**——那通常就是分析器第一个卡住的位置。
```

弱写法（平文本平铺 + 狂甩未解释术语 + 无主线案例）：

> 分析器负责对查询语句进行词法分析与语法分析，生成抽象语法树（AST）并交由预处理器检查表和列的元数据语义。若存在词法或语法错误，解析器会向客户端协议层返回错误码。随后优化器基于代价模型（CBO）计算不同访问路径的 I/O 与 CPU 成本并生成执行计划。

AI 写作警惕词和禁用句式见 `references/anti-ai-writing.md`。

常见学习链路：

```text
问题入口 -> 人话直觉 -> 术语和边界 -> 例子/代码/案例 -> 判断标准 -> 互动练习 -> 收束
```

这条链路是检查缺口用的，不是每节都要按同一顺序、同一组标题展开。入口可以是失败现象、成品预览、一道题、一个数据集或材料中的原例；解释也可以按时间、因果、对比、推导或动手步骤推进。

中文课件应当让学习者在每章结束时知道三件事：

- 这章到底解决了什么问题。
- 我现在能判断、能解释、能动手做什么。
- 哪些地方我还容易混，下一次学习从哪里接上。

## 课程层次

**技术主题：**

```text
基础入门 -> 建立概念，跑通第一个程序
核心能力 -> 深度讲解，动手实践
进阶实战 -> 原理深挖，项目/面试/考试应用
```

**非技术主题：**

```text
基础入门 -> 建立概念框架，理解核心问题
深层理解 -> 关键理论、案例、推导
批判拓展 -> 不同学派、前沿讨论、自选专题
```

这些是课程级层次，不是固定比例。两小时速成课可以只保留基础和核心；材料驱动课按材料本身的层次走；已经具备前置的学习者可以从核心能力开始。

## 自然章节结构

不要把课件写成固定模板。每章必须形成学习闭环，但标题和组织方式要跟主题走。

一章对应一个可折叠模块，模块根目录的 `content.md` 只写章节前言：

- 这章要解决的核心问题。
- 学习者需要具备的前置条件；缺了就指出本章会补哪一小段。
- 本章小节目录，每个小节解决什么问题；具体文件和导航规则看 `courseware-format.md`。
- 本章完成后能做出的判断、解释或操作。

真正的正文写进小节文件。小节拆分、合并和导航链接规则以 `courseware-format.md` 为准；这里强调中文写法：系统精讲和考试备考按 phase-2-generation.md 的模块结构护栏和拆分规则组织小节；每个小节必须能独立学习。

小节正文自然包含这些内容，不要求固定标题：

- 用真实问题、错误现象、工作场景或反直觉点开场。第一段不列出 2 个以上未解释的术语。
- 先用人话建立直觉，再给准确术语；首次概念介绍按 `courseware-format.md` 的规则处理，中文里要顺手解释，不要让学习者靠上下文猜。
- 用 2-5 个样本数据、不超过 10 行的代码或一个具体案例起步，再过渡到真实规模。
- 在概念旁边给判断标准：什么时候用，什么时候不用，和相似概念怎么区分。
- 如果 Phase 1 调研从课程教材、真题或权威资料中找到已知误解，放在相关知识点旁边拆解；否则不写。
- 需要学习者作答时，用 `study-*` 题块；链接、题块和导出规则看 `courseware-format.md`。
- 小节末尾可以自然收束 2-5 条要点；不要写空泛的“建议下一步”。

中文正文必须落实 `courseware-format.md` 的共享教学完整性规则。中文写法上的落点是：把资料讲成讲义，补前置、加过渡、换成人话、用小例子垫一下，再进入原材料里的术语、图、公式、代码或结论；不要写成资料汇编、关键词清单或压缩笔记。

考试备考课里，“重点清单”只能当导航，不能当正文。具体深度门禁由 `phase-2-generation.md` 负责；中文正文要把重点写成能答题的讲义，而不是把“重点掌握”四个字换个说法。

成熟中文教程通常不是“先给目录，再给定义”，而是把一个问题顺着讲完：先有问题入口，再贴近原材料给图、代码、例题、公式或表格，接着解释每一步在解决什么，最后用练习把学习者拉回来。生成课程时沿用这种推进方式。用户提供或许可允许复用的课件、教材和题目如果本身讲得好，可以保留较长原句、原图、原表和原题；其他外部教程借鉴讲解顺序、例子结构和必要短引，按 `courseware-format.md` 的来源规则重讲。

## 初学者入口要求

系统精讲不是把所有概念压进一章。面向初学者或弱前置学习者时，每个基础模块必须先搭入口，再进入术语和公式。

基础模块必须满足：

- 开头先给一个具体问题或场景，不要第一段就堆定义。
- 每个核心术语或核心概念第一次出现时，用一句人话解释它“在解决什么问题”。
- 第一个例子使用 2-5 个样本数据或日常/工程场景；不要直接使用真实模型规模、论文公式或复杂代码。
- 从例子到抽象概念之间要有过渡句，说明“这个小例子和真实系统哪里一样，哪里不一样”。
- 如果学习者画像里写着数学、语言、工具前置薄弱，要在相关小节补一个“够用前置”，只讲当前小节马上会用到的部分。
- 不要把官方链接、练习题或扩展阅读提前到概念还没讲清楚之前。

弱写法：

> 向量是有序数列，矩阵是二维数组，张量是多维数组。Transformer 输入张量形状为 `[batch, seq, hidden]`。

好写法：

> 先想一个问题：模型看到一句话时，电脑里到底放的是什么？它不是中文句子，也不是 Java 对象，最后只能是一堆数字。我们先从一句 4 个词的小句子开始看，每个词用 8 个数字表示，这样才能一步步理解 `[batch, seq, hidden]`。

## 反面教材开场（初学者的 Pain-First 适配）

面向初学者的小节，可以先展示一个一眼就能看出不对的写法或场景，再引出正确思路。这不同于 `teaching-patterns.md` 的通用"痛苦先行"模式——初学者的失败场景必须是感性可理解的（"这段代码怎么会崩？""这个数据怎么全变成 NaN 了？"），不需要技术背景才能看懂。

具体模式和结构以 `teaching-patterns.md` 模式 1（痛苦先行）和模式 5（错误驱动教学）为准；本节只规定中文初学者的入口风格。

## 代码走读的中文表达

当采用 `teaching-patterns.md` 模式 4（手把手跟踪）时，中文课件中的走读表达遵循以下规则：

- 走读结构以 `teaching-patterns.md` 模式 4 为准，这里不重新定义。
- 每一步状态变化用中文短句标注，不翻译英文变量名。
- 最终总结用中文简单句："最终的执行顺序是 part1 → part3 → Handler → part4 → part2。"

## 中文题目写法

题块类型、字段、答案展示时机和纯题目小节规则以 `courseware-format.md` 为准；这里不重写 schema。中文题目要像老师当面出题：题干说清任务、材料、限制和作答角度，别只写“请分析”“谈谈理解”。

题量不重要，重要的是每题能暴露一个具体的理解缺陷。面试题要问出判断标准，考试题要给足题面数据，代码题要有输入输出或错误现象，理论题要说明要辨析、证明、反驳还是套公式。

## 中文表达原则

### 1. 先讲清真实作用，再给术语名称

先用直白的日常语言把“这个东西在真实系统里干什么、解决什么具体麻烦”讲明白，再给出课本或文档里的正式术语。

好写法：

> 函数执行完之后，它内部的局部变量本来就销毁了；如果返回的子函数还想继续读写外层函数当时的变量，就得把那几个变量一起打包留下来。这种“函数带着它周围变量一起走”的机制，正式名称叫闭包（Closure）。

弱写法（学术定义先行）：

> 闭包（Lexical Closure）是由函数及其词法环境组合而成的实体。

弱写法（俗套比喻绕弯）：

> 闭包就像一个背着小书包去春游的小朋友，妈妈（外层函数）虽然回家了，但小书包里还装着妈妈塞给他的零食（变量）。

### 2. 慎用比喻，优先用最小真实案例

除非学习者画像明确记录了某个已掌握的技术栈（如会 Java 学 Python，可点明对应机制与差异），否则不要编造生活比喻。把复杂系统缩小成只有 2 个变量、3 行代码或 4 个内存格子的**最小真实案例**，直接推演真实机制，比任何打比方都更清晰、心智负担更低。
