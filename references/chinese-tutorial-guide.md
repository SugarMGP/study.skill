# 中文教程写作规范

> 综合参考：阮一峰、廖雪峰、JavaGuide、CS-Notes、Rust 中文社区教程、ai-agents-from-zero、极客时间等中文教程的常见写法。

本文件只规定中文课件的表达、章节组织和中文读者体验。图表、图片、代码、可保存练习块等跨语言课件格式看 `courseware-format.md`。

## 核心取向

中文教程要像一个认真带人的师傅：先把问题讲明白，再带学习者动手或推理，最后确认他是不是真的会了。不要写成资料汇编，也不要写成静态题库。

推荐主线：

```text
为什么要学 -> 先记住一句话 -> 例子/代码/案例 -> 判断标准 -> 互动练习 -> 本章收束
```

好的中文课件应当让学习者在每章结束时知道三件事：

- 这章到底解决了什么问题。
- 我现在能判断、能解释、能动手做什么。
- 哪些地方我还容易混，下一次学习从哪里接上。

## 三层递进结构

**技术主题：**

```text
第一层：基础入门（30%）-> 建立概念，跑通第一个程序
第二层：核心能力（40%）-> 深度讲解，动手实践
第三层：进阶实战（30%）-> 原理深挖，项目/面试/考试应用
```

**非技术主题：**

```text
第一层：基础入门（30%）-> 建立概念框架，理解核心问题
第二层：深层理解（40%）-> 关键理论、案例、推导
第三层：批判拓展（30%）-> 不同学派、前沿讨论、自选专题
```

## 单章写作模板

每章必须有目标、前置提醒、主体讲解、互动练习和收束。标题可以随主题调整，不要为了套模板写废话。

```markdown
# 第 X 章：{标题}

## 这一章你要学会什么

学完这一章，你应该能：

- {用自己的话解释一个核心概念}
- {在具体场景里做出一个判断或改动}
- {说明一个关键取舍，而不是只背定义}

## 开始前先确认

- {需要知道的前置概念、材料、工具或时间}
- {如果缺少前置条件，先补哪一小段}

## 先记住一句话

{10-25 字的直觉总结。它必须能独立成立，不要写口号。}

## X.1 {节标题}

{先用人话建立直觉，再给准确术语。}

{例子、代码、案例或推导。技术主题给命令和预期输出；非技术主题给具体场景和判断过程。}

{如果这里有官方文档、教材、论文或源码能帮助深入理解，放一条短链接，并说明它适合查什么。}

{如果学习者画像里有相关经验，例如 Java、后端、数学、写作经验，可以用一句迁移类比帮助理解；类比有边界时要说清边界。}

{把判断标准说清楚：什么时候用、什么时候不用、和相似概念怎么区分。}

{如果这里有真实常见误解，就顺手拆掉；没有就不要硬写。}

### 练一下

{放一个小任务或一个需要作答的题。需要保存答案时，使用 `courseware-format.md` 里的 `study-*` 题块。}

## X.2 {节标题}

{逐步加深，仍然保持“概念 -> 例子 -> 判断 -> 练习”的节奏。}

## 本章收束

### 带走这几件事

- {一句话概括本章主问题}
- {最关键的概念关系或判断标准}
- {本章能迁移到什么场景}
- {如果存在真实高频误区，用一句话提醒；没有就省略}

### 互动题

{放 1-3 道必须先作答的 `study-recall` 或 `study-transfer`。学习者提交后，阅读器才显示参考思路。}

### 章末检查

{需要时放一个 `study-checkpoint`，引用本章前面出现过的练习。}

### 下一次从哪里接上

{只写具体动作，例如“把示例里的 X 改成 Y 再跑一次”“用本章判断标准分析案例 B”“进入第 X 章前先完成 checkpoint”。如果只是“进入下一章”，就不要写。}
```

每章建议 2-4 个小节。一个小节只承载一个主要概念；如果超过 4 个二级知识点，拆成下一章。

## 章末互动题写法

章末不要再写静态的“思考题 + 参考答案”。只要题目需要学习者作答，就用本地阅读器支持的 `study-*` 题块。

使用规则：

- 概念回忆题用 `study-recall`，检验能不能说清基本概念。
- 场景分析、方案选择、面试题、考试大题优先用 `study-transfer`，因为它要求换场景应用。
- 费曼解释（用自己的话讲明白）用 `study-feynman`。
- 模块末尾需要综合检查时，用 `study-checkpoint` 引用前面的题。
- `answer` 里写“参考思路/解析/回答要点”，不要只写一个结论。
- 面试导向模式下，面试题也写成 `study-transfer`；`answer` 里包含回答要点、常见追问和判断标准。

示例：

````markdown
### 互动题：Redis 为什么快？

先按自己的话写 3 点，不要直接看答案。

```study-transfer
id: 03-redis-fast-interview
question: 面试官问“Redis 为什么快”，你会怎么答？请写出 3 个原因，并说明它们分别解决了什么问题。
hints:
  - 不要只说“因为在内存里”
  - 想想数据结构、网络模型和线程模型
  - 顺手想一想 Redis 什么时候也会变慢
answer: >-
  参考思路：先说内存访问是基础，再补充高效数据结构、I/O 多路复用和单线程避免大量锁竞争。
  回答时要说清“快在哪里”，也要知道持久化、慢查询、大 key、网络瓶颈会让它变慢。
  常见追问：为什么单线程还能快？Redis 6 之后多线程主要解决什么？
  判断标准：能否把原因和具体瓶颈对应起来，而不是背几个关键词。
```
````

不要在同一章塞太多题。题目少一点，但要真的能暴露理解问题。

## 中文表达原则

### 1. 先讲人话，再给术语

先用日常语言建立直觉，再给出精确术语。

好写法：

> 可以把 Hook 理解成一个钩子：它把 React 的状态能力钩到函数组件上，让函数组件也能记住数据。这个钩子的学名叫 `useState`。

弱写法：

> `useState` 是 React 的一个 Hook API，用于在函数组件中管理状态。

### 2. 核心概念要有抓手

能类比就类比，优先用学习者熟悉的生活经验或已学知识。类比必须说明边界：哪里像，哪里不像。

没有好类比时，不要硬编。改成从一个更简单的问题一步步推出来。

### 3. 使用“先记住一句话”

核心概念开头给一句 10-25 字的直觉总结：

> **先记住一句话：** 闭包就是函数记住了它出生的地方。

这句话要帮学习者抓住主线，不能写成“某某很重要”这种空话。

### 4. 判断标准要明确

不要只说“是什么”，还要说明：

- 什么时候用？
- 什么时候不用？
- 和相似概念怎么选？
- 看到什么现象，说明理解可能错了？

能用对比表格就用表格；表格讲不清时，用两个具体场景对比。

### 5. 示例和练习要贴近中文读者

**技术主题：**

- 代码注释使用自然中文，不写英文注释的直译版。
- 展示运行命令和预期输出。
- 需要依赖版本时写清楚版本；未执行验证时必须明说。

**非技术主题：**

- 每个关键概念配一个具体案例。
- 推导过程不要跳步。
- 练习可以是辨析题、论述题、场景分析或材料题。
- 标注必要来源，不大段复制原文。

### 6. 官方资料要嵌在知识点旁边

不要把官方文档和资源全部塞到课程末尾。讲到具体 API（应用程序接口）、概念、定理、工具命令时，如果有高质量官方或权威资料，就在旁边补一条短链接。

好写法：

> 深入看：React 官方文档的 [`useState`](https://react.dev/reference/react/useState) 页面适合查参数、返回值和常见用法；先学完本节再看，不要一开始就陷进 API 细节。

写法要求：

- 链接必须服务当前知识点，不要堆资源列表。
- 一句话说明“为什么现在看这个链接有用”。
- 技术主题优先官方文档、标准、源码；非技术主题优先教材、论文、课程大纲或权威资料。
- 课程级来源放在课程概览或大纲里；不要默认生成一个孤立的 `resources.md`。
- 只有用户明确要资料包，或课程确实需要一个从正文链接过去的扩展阅读附录，才单独生成资源文件。

### 7. 用学习者已有经验做迁移

如果学习者画像里记录了已会语言、工具或领域经验，要主动利用，但不要硬套。

示例：

- 学过 Java 再学 Python 装饰器：可以先类比成“给函数包一层可复用处理”，再强调它不是 Java 注解，运行时机制不同。
- 有后端经验再学 React 状态：可以把状态理解成“组件自己的内存”，但要说明它不是服务器缓存，更新会触发渲染。
- 有数学基础再学机器学习：可以用函数、向量和优化来解释，但不要默认他懂工程实现。

规则：

- 类比只在能缩短理解路径时使用。
- 类比必须说明边界：哪里像，哪里不像。
- 薄弱前置只补当前章节需要的一小段，不要偏题变成另一门课。

### 8. 误解和坑点就地拆

真实常见误解要写，但不要凑数量，也不要固定做成“踩坑表”。它应该自然出现在相关知识点旁边。

可用写法：

- “这里容易误会的是……”
- “如果你看到……，先查……，别急着……”
- “这个问题只在……场景下会出现；平时不用提前焦虑。”
- “它和 XXX 不一样，关键区别是……”

没有真实来源、真实经验或清晰场景时，不要写“常见陷阱”。

### 9. 版本说明只在影响学习时写

技术主题只有在 API（应用程序接口）、语法、工具链或依赖有破坏性变化时才写版本说明。

非技术主题标注教材版次、论文年份或数据时间即可，不硬凑“版本变化”。

### 10. 面试题不要变成背答案

面试导向模式下，每章可以关联 1-3 道典型题，但必须让学习者先作答。题目用 `study-transfer`，参考内容写在 `answer` 中。

`answer` 至少包含：

- 回答要点：应该覆盖哪些点。
- 追问方向：面试官可能继续问什么。
- 判断标准：什么回答算理解了，什么回答只是背词。

不要把面试题写成静态 Markdown 列表，也不要只给“标准答案”。

### 10.5 术语、题库和闪卡不要旁路化

不要默认生成 `glossary.md`、`practice.md`、`interview-qa.md`、`exam-practice.md`
或 `flashcards.csv`。这些文件如果后续没人打开，就只是在制造“看起来很完整”的错觉。

更好的写法：

- 术语第一次出现时顺手解释；术语多时，在本章末尾写“术语速查”。
- 面试题、考试题和课后练习写进本章，用 `study-transfer` 或 `study-checkpoint` 让学习者先答再看解析。
- 复习问题来自已学过的关键概念，由学习阶段写入 `concepts.json`，不要在课程生成阶段预制一堆没学过的闪卡。
- 用户明确要 Anki CSV、打印题册、术语表时可以导出，但必须在课程概览或相关章节里说明它怎么用。

### 11. 本章收束要有信息量

小结不是把标题抄一遍。它应该帮学习者完成整理：

- 本章主问题是什么。
- 本章最重要的 3-6 个概念或判断标准是什么。
- 哪个例子最能代表本章方法。
- 下一章会接着解决什么缺口。

如果没有具体下一步，就不要写“建议下一步”。空泛的“完成练习后进入下一章”没有价值。

## 中文禁忌

- 不要英文直接机翻；用中文思维重写。
- 不要堆术语不解释。
- 不要只给代码不给运行命令和预期输出。
- 不要只讲是什么，不讲为什么和怎么选。
- 不要忽略影响学习结果的版本变化。
- 不要大段照搬官方文档；在具体知识点旁边放短链接即可。
- 不要写 AI 腔：夸大意义、三段式排比、空洞连接词、宣传话术。
- 不要为凑结构硬写“常见陷阱”“建议下一步”“面试题”。
- 不要默认生成后续学习流程不会读取的旁路文件。
