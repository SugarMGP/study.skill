# 教学技巧模式库

> 可复用的教学结构模板。Phase 2 按概念类型选用。

本文件定义推荐使用的教学结构模板（推荐侧）。AI 写作中应避免的特征（禁止侧）见 `anti-ai-writing.md`。两个文件互补，不重叠。

**核心约束**：这些模式是工具箱，不是清单。每个小节选用 2-4 个最适合的模式即可，不要全部套用。

---

## 模式 1：痛苦先行（Pain-First）

| 维度 | 内容 |
|------|------|
| 适用 | 引入一个"解决已知问题"的新概念时 |
| 结构 | ① 展示会出错的场景（完整代码/数据/错误输出）→ ② 让学习者看到具体问题现象 → ③ 解释根因 → ④ 引入新概念作为解决方案 → ⑤ 展示修复后结果 → ⑥ 对比前后差异 |
| 错误来源 | **必须来自 Phase 1 调研记录中收录的源材料片段**——官方文档中的常见错误示例、教材中的反例、社区公认的错误模式总结。禁止 agent 凭空编造一个"看起来会出错"的代码 |
| 示例 | Rust 所有权章：先用 C 代码展示悬垂指针 → 再介绍 Rust 所有权如何解决 |
| 禁止 | 先给定义再给正确示例；从不展示"如果不这样做会怎样"；编造不存在的错误场景 |
| 初学者注意 | 失败场景必须是学习者能**直觉理解**的（不是技术层面），且必须在同一小节内解决，不能让挫败感持续 |

## 模式 2：渐进形式化（Progressive Formalization）

| 维度 | 内容 |
|------|------|
| 适用 | 引入公式、算法或抽象模型时 |
| 结构 | ① 具体例子（带真实数据/变量名）→ ② 一般化公式 → ③ 向量化/符号化形式 → ④ 批量/系统级形式。每层之间解释为什么泛化 |
| 示例 | dd2l.ai Ch3 线性回归：`price = w_area·area + w_age·age + b` → `ŷ = w_1x_1 + ... + w_dx_d + b` → `ŷ = wᵀx + b` → `Ŷ = Xw + b` |
| 禁止 | 跳过中间层直接给最简形式 |
| 与现有规则关系 | 本模式是 `chinese-tutorial-guide.md` "小例子→真实规模" 流程的强化版，增加了多层形式化结构 |

## 模式 3：崩溃证明（Collapse Proof）

| 维度 | 内容 |
|------|------|
| 适用 | 引入一个"如果不加就会退化/失败"的关键机制时 |
| 结构 | ① 构建缺少该机制的版本 → ② 用数学/代码证明它会退化 → ③ "所以我们需要 X" → ④ 加入 X 后展示效果 |
| 示例 | dd2l.ai Ch4.1：证明无激活函数的多层网络退化为单层线性变换（O = X·W^(1)·W^(2) = X·W） |
| 禁止 | 直接说"我们需要 X 因为这样更好" |

## 模式 4：手把手跟踪（Hand-Execution Trace）

| 维度 | 内容 |
|------|------|
| 适用 | 递归、链式调用、回调、中间件等执行流程不直观的代码 |
| 结构 | ① 展示完整代码 → ② 设定具体输入 → ③ 逐步模拟执行，标注每一步状态变化 → ④ 一句话总结最终顺序 |
| 示例 | geektutu Day 5 中间件链：`c.index = -1` → `c.Next()` → `c.index = 0` → 调用 A → A 执行 part1 → `c.Next()` → `c.index = 1` → ... → 最终顺序 `part1 → part3 → Handler → part4 → part2` |
| 验证约束 | 跟踪结果必须与已知正确输出对照（官方文档、教材或实际代码执行）。若 agent 无法实际运行验证，必须在聊天交付中标注"跟踪为示意，未经执行验证"，且不得作为唯一教学依据 |
| 禁止 | 用变量名模拟（必须用具体值）；跳过中间步骤 |

## 模式 5：错误驱动教学（Error-Driven Teaching）

| 维度 | 内容 |
|------|------|
| 适用 | 编译器/解释器报错、数据库约束违反、API 错误返回等 |
| 结构 | ① 展示"看起来合理"但会出错的代码 → ② 展示**完整**错误输出（保留原始格式，中文旁注关键行） → ③ 分析根因 → ④ 展示修复方案 → ⑤ 解释为什么修复有效 |
| 错误来源 | **必须来自 Phase 1 调研记录中收录的源材料片段**——官方文档中的常见错误示例、教材中的反例、社区公认的错误模式总结。禁止凭空编造 |
| 示例 | Rust Course 所有权章：`let s2 = s1; println!("{}", s1);` → 完整编译器错误 → 解释 move 语义 |
| 禁止 | 截断错误输出；只给正确代码不展示错误 |

## 模式 6：双重实现（Dual Implementation）

| 维度 | 内容 |
|------|------|
| 适用 | 教框架/库时 |
| 结构 | ① 手写实现（纯语言，不依赖框架）→ ② 学习者理解了底层 → ③ 用框架 API 重写 → ④ 明确指出框架哪一行替代了手写哪一段 |
| 示例 | dd2l.ai 每章"从零实现→简洁实现"；RethinkFun Ch8 手写 MNIST → PyTorch MNIST |
| 禁止 | 直接给框架 API 调用不经手写版本 |

## 模式 7：代码即画布（Code-as-Canvas）

| 维度 | 内容 |
|------|------|
| 适用 | 张量/矩阵/多维数据的短代码（<~30 行教学代码） |
| 结构 | ① 每个操作有形状标注：`# (batch, seq_len, d_model) --> (batch, h, seq_len, d_k)` → ② 每个关键行有"为什么"注释（不是"做什么"） → ③ 数学公式以 LaTeX 形式写在对应代码旁边 |
| 示例 | RethinkFun transformer.py |
| 与现有规则关系 | 较长代码（>~30 行）使用现有 `courseware-format.md` 的"完整示范"标准即可，不需要逐行标注 |

## 模式 8：难度预期管理（Difficulty Framing）

| 维度 | 内容 |
|------|------|
| 适用 | 高难度模块——用客观事实管理学习者预期，不编造个人经历 |
| 结构 | 在模块/小节开头或结尾用 1-2 句客观说明难度和原因：<br>"这一节涉及多层嵌套调用，跟着代码一步步走就行，不要跳读。"<br>"这个概念在社区里公认比较绕——核心原因：状态太多。我们一次只追一个状态。"<br>"这里有两个容易混的点，学完记得对照一下末尾的对比表。" |
| 禁止 | 编造个人经历（"我第一次学的时候""我踩过的坑"）<br>空洞鼓励（"继续加油""你已经很棒了"）<br>假装情感（"写到这我都快崩溃了"——真人作者可以说，AI agent 不能说） |
| 核心原则 | 用客观事实管理学习者预期，不用虚构经历假装共情 |

## 模式 9：学习实验室（Learning Laboratory）

| 维度 | 内容 |
|------|------|
| 适用 | 可视化概念、参数效果等探索性内容 |
| 结构 | 生成独立可运行脚本 → 脚本中保留注释掉的替代方案（`#transform = ...`）→ 打印可对比输出 |
| 示例 | RethinkFun Augmentation.py：原始图像 → 注释掉的多种 transform 供学习取消注释和重跑 |
| 禁止 | 把探索性内容写成纯说明文字 |

## 模式 10：类比双层映射（Two-Level Analogy）

| 维度 | 内容 |
|------|------|
| 适用 | 多个相关概念需要同时解释时 |
| 结构 | 用一个生活场景同时映射多个概念的关系 + 必须说明类比边界（哪里不像） |
| 示例 | Rust Course："餐馆——桌子=堆内存、桌号=栈指针、服务员=OS 分配器。但餐馆桌子可以随便拼，内存分配有对齐要求。" |
| 禁止 | 简单的一对一比喻（除非概念本身很简单）；不说明边界 |

## 模式 11：嵌入式预判提问（Anticipatory Q&A）

| 维度 | 内容 |
|------|------|
| 适用 | 任何可能产生疑问处 |
| 结构 | 讲完概念后立刻插入"你可能会想：XXX？"→ 自问自答 |
| 示例 | Rust Course 生命周期消除规则："爱思考的读者肯定要问了，如果返回值的生命周期跟参数的不一样怎么办？——答案是..." |
| 禁止 | 把所有问题集中到章末 FAQ |

## 模式 12：目标预览（Destination Preview）

| 维度 | 内容 |
|------|------|
| 适用 | 构建/实现类课程的模块或小节开头 |
| 结构 | 先展示最终产物（代码/效果/输出）→ "这是我们要达到的目标。现在开始一步步构建。" |
| 示例 | geektutu Day 2：先展示完整 `main.go` 的最终用法（路由注册 + JSON 响应 + HTML 渲染），再讲 Context 如何实现 |
| 禁止 | 纯概念讲解使用此模式 |

## 模式选用指南

根据概念类型选择最适合的 2-4 个模式：

| 概念类型 | 推荐首选模式 |
|----------|-------------|
| 解决已知问题的新工具/机制 | 痛苦先行(#1)、崩溃证明(#3) |
| 数学公式/算法 | 渐进形式化(#2) |
| 执行流程不直观的代码 | 手把手跟踪(#4) |
| 编译器/运行时错误相关 | 错误驱动教学(#5) |
| 框架/库学习 | 双重实现(#6) |
| 张量/矩阵操作 | 代码即画布(#7) |
| 高难度模块 | 难度预期管理(#8) |
| 可视化/参数探索 | 学习实验室(#9) |
| 多概念关系 | 类比双层映射(#10) |
| 任何可能产生疑问处 | 嵌入式预判提问(#11) |
| 构建/实现类 | 目标预览(#12) |

---

## 模式组合禁忌

- **痛苦先行 + 目标预览互斥**：先展示失败再展示目标会造成混乱——选一个
- **零基础学习者**：优先用目标预览、类比双层映射、渐进形式化；痛苦先行只用直觉可理解的失败场景
- **考试备考模式**：优先用错误驱动教学、渐进形式化、嵌入式预判提问；跳过学习实验室（耗时）
- **速成模式**：优先用目标预览、双重实现；跳过崩溃证明（需要完整推导）
